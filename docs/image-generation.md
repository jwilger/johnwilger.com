# Subscription image generation in Pi

Use `codex_generate_image` for Impeccable comps and ordinary raster assets in this checkout. The project loads the tool from a pinned local package; it doesn't load the package's duplicate imagegen skill. Nothing runs on startup other than tool registration.

## Sign in and use the tool

1. In a terminal, run `pi auth login openai-codex` and complete the browser sign-in. This is separate from Pi's newer `openai` (“Sign in with ChatGPT”) login; you can keep using that provider for conversation. Do not copy tokens between clients or print them. Check this login with `pi auth check --provider openai-codex --no-refresh`; expect `ready`.
2. In interactive Pi, reload if the tool isn't listed yet. For a quick check, ask Pi to call `codex_generate_image` with a synthetic prompt, `save: "project"`, and an explicit `outputPath` under `.build/`. The parent directory must exist, and the tool won't overwrite an existing file.
3. For Impeccable, use the exact project-relative `comp` or `plate` PNG path rather than the tool's default location. For an approved crop, pass it in `referencedImagePaths`; interactive Pi asks before sending local images to OpenAI. Use this as the native image tool in the Pi workflow; it does not change what Impeccable's own `generate-image` API command or other harnesses use.

The tool always requests `background: "auto"`. It can produce opaque PNGs; do not claim it can reliably make genuine alpha. For a cutout, inspect the actual alpha rather than accepting a painted checkerboard. If genuine alpha is unavailable, report the blocker. Codex CLI's official image tool supports a transparency option, but the installed CLI timed out before the image tool could run. Don't silently switch to a billed API or another service.

## Dependency review — 0.2.2

- **Why:** Impeccable needed an image tool that could use the existing subscription and save at a specified PNG path. The installed Pi `openai-codex` provider has no native image model. The newer `openai` login explicitly [does not support image generation in its current preview](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations).
- **Source and pin:** `@crazygit/pi-codex-image-gen` [0.2.2 from npm](https://registry.npmjs.org/@crazygit/pi-codex-image-gen/-/pi-codex-image-gen-0.2.2.tgz), MIT, `gitHead` `ba229944a876d48d2cf4cd416aec722deb24f52c` in the [public source repository](https://github.com/crazygit/pi-codex-image-gen). The npm integrity below matched the fetched bytes. The local package starts from the published artifact, with small Pi 1.6.0 compatibility fixes: TypeBox literal unions preserve the tool's enum types, provider headers set to `null` are omitted, and empty reference lists are normalized without mutating the request. Loading uses Pi's existing peers; it doesn't run npm or download the package. No install lifecycle hook or runtime dependency beyond those peers. This is a small third-party project, not an OpenAI-supported integration.
- **Privileges and data:** The extension uses Pi's registry to resolve the `openai-codex` token and extracts its account claim. Tool calls send the prompt and any approved reference bytes to `chatgpt.com/backend-api/codex/images/{generations,edits}`. The client rejects redirects and bounds the response. On some rate-limit or gateway responses it can try up to three times total. Reviewed the auth, request/response, reference planning and reread, and output-writing paths. The tool does not independently read credential files or spawn subprocesses. Use a trusted checkout and explicit in-project destinations; upstream also supports saving under the global Pi directory or requesting approval for other paths. Generated images are returned to Pi as tool output as well as written to disk, so the image may also be in the conversation context and session history.
- **Evidence:** Pi 1.6.0 loaded the unchanged package in an isolated run. A fake backend returned a valid PNG at the requested path, and a blank prompt made no image request. With explicit user approval a separate run used a temporary in-memory credential shim for the existing Codex CLI token, one synthetic generation request, no references, no API key, and no repo context. HTTP 200 returned a valid 1536×1024 PNG. That proved the legacy subscription route. It did not exercise a normal `pi auth login openai-codex` or live reference uploads. Codex CLI 0.170.0 failed twice at workspace routing, including with the reported `log_dir` workaround.
- **Revisit:** Review changes and repeat the blank-prompt and output-path tests at an upgrade. Reassess if auth or endpoints change, rate limits cause friction, or Pi offers a supported subscription image tool. Remove the vendored package if a supported route meets the same needs. Do not persist the credential shim used by the smoke test.
